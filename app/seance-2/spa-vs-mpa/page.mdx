# SPA vs MPA : Architecture des applications web

Avant de plonger dans React, il est essentiel de comprendre **quel type d'application** vous allez construire. React est principalement utilisé pour créer des **SPA** (Single Page Applications).

---

## Qu'est-ce qu'une SPA ?

**SPA** = **Single Page Application** (Application à Page Unique)

Une SPA est une application web qui **charge une seule page HTML** au départ, puis met à jour dynamiquement le contenu **sans recharger la page complète**.

### Fonctionnement d'une SPA

```
┌─────────────────────────────────────────────┐
│  Première visite                            │
│  ────────────────                           │
│  1. Navigateur demande index.html          │
│  2. Serveur envoie HTML + JavaScript       │
│  3. JavaScript s'exécute                    │
│  4. Application React prend le contrôle    │
└─────────────────────────────────────────────┘

┌─────────────────────────────────────────────┐
│  Navigation suivante (ex: clic sur un lien)│
│  ──────────────────────────────────────────│
│  1. JavaScript intercepte le clic          │
│  2. Met à jour l'URL (sans recharger)      │
│  3. Récupère les données (API si besoin)   │
│  4. Re-render les composants React         │
│  → Pas de rechargement de page !           │
└─────────────────────────────────────────────┘
```

### Exemple concret

Imaginez Gmail :
- Vous chargez Gmail **une seule fois**
- Quand vous cliquez sur un email, **seul le contenu change**
- La page ne se recharge **jamais**
- L'URL peut changer (`/inbox` → `/sent`) mais sans rechargement

<Callout type="info" title="React = SPA par défaut">
Quand vous créez une application avec **React seul** (avec Vite), vous créez une **SPA**.

Le serveur envoie un fichier HTML quasi-vide, puis React génère tout le contenu côté client (dans le navigateur).
</Callout>

---

## Qu'est-ce qu'une MPA ?

**MPA** = **Multi-Page Application** (Application Multi-Pages)

Une MPA est une application web **traditionnelle** où chaque navigation charge une **nouvelle page HTML complète** depuis le serveur.

### Fonctionnement d'une MPA

```
┌─────────────────────────────────────────────┐
│  Chaque navigation                          │
│  ─────────────────                          │
│  1. Utilisateur clique sur un lien         │
│  2. Navigateur fait une requête au serveur │
│  3. Serveur génère une nouvelle page HTML  │
│  4. Navigateur charge et affiche la page   │
│  → Écran blanc pendant le chargement       │
└─────────────────────────────────────────────┘
```

### Exemple concret

Sites web classiques (WordPress, forums, etc.) :
- Vous visitez `/accueil` → Le serveur envoie `accueil.html`
- Vous cliquez sur `/contact` → Le serveur envoie `contact.html`
- À chaque clic, **la page se recharge complètement**
- L'écran devient blanc pendant le chargement

<Callout type="tip" title="MPA = Architecture traditionnelle">
Les MPA existent depuis les débuts du web. C'est l'approche classique où le **serveur génère le HTML**.

Exemples : PHP, WordPress, Ruby on Rails (sans JS), Django, etc.
</Callout>

---

## Comparaison SPA vs MPA

| Critère | SPA | MPA |
|---------|-----|-----|
| **Chargement initial** | Plus lent (tout le JS à charger) | Plus rapide (seulement le HTML) |
| **Navigation** | ⚡ Instantanée (pas de rechargement) | 🐢 Plus lente (rechargement complet) |
| **Expérience utilisateur** | Fluide, app-like | Saccadée (flash blanc) |
| **SEO** | ⚠️ Difficile (contenu généré en JS) | ✅ Facile (HTML prêt) |
| **Complexité** | Plus complexe (routing client, état) | Plus simple (serveur fait tout) |
| **Backend** | Séparé (API REST/GraphQL) | Intégré (génère le HTML) |
| **Offline** | Possible (avec cache) | Impossible |
| **Exemple** | Gmail, Twitter, Spotify Web | WordPress, Forums, Sites vitrines |

## Avantages des SPA

### ✅ Expérience utilisateur fluide

**Navigation instantanée :**
```
Utilisateur clique sur "Profil"
→ Pas de rechargement
→ Transition animée
→ Contenu apparaît immédiatement
```

C'est ce qui donne l'impression d'une **vraie application** (comme sur mobile).

### ✅ Séparation frontend/backend

```
┌──────────────┐         API          ┌──────────────┐
│   Frontend   │ ◄────────────────► │   Backend    │
│   (React)    │   JSON uniquement   │   (Node.js)  │
└──────────────┘                      └──────────────┘
```

- Frontend et backend sont **complètement séparés**
- Même API pour le web, mobile, desktop
- Équipes peuvent travailler indépendamment

### ✅ Interactions riches

Possible de créer des UI complexes :
- Drag & drop
- Animations fluides
- Mises à jour en temps réel (WebSockets)
- Formulaires multi-étapes avec validation instantanée

### ✅ Réutilisation de composants

```tsx
// Un composant Button utilisable partout
<Button variant="primary">Envoyer</Button>
<Button variant="secondary">Annuler</Button>
```

React encourage la **réutilisation** et la **composition**.

## Inconvénients des SPA

### ❌ Chargement initial lent

```
Première visite d'une SPA :
1. Télécharger HTML (petit)
2. Télécharger JavaScript (gros !) ← Peut être lent
3. Exécuter le JavaScript
4. Enfin afficher le contenu
```

Si votre bundle JavaScript fait 500 KB, l'utilisateur doit attendre tout ça.

<Callout type="warning" title="Performance initiale">
**Problème :** L'utilisateur voit un écran blanc pendant le chargement du JS.

**Solutions :**
- Code splitting (charger seulement ce qui est nécessaire)
- Lazy loading (charger à la demande)
- Optimisation du bundle
- → Ou utiliser un framework hybride (Next.js)
</Callout>

### ❌ SEO difficile

**Le problème :**

```html
<!-- Ce que le serveur envoie (SPA) -->
<html>
  <body>
    <div id="root"></div>
    <script src="bundle.js"></script>
  </body>
</html>
```

Google et les moteurs de recherche voient un **HTML vide** !

Le contenu est généré par JavaScript, mais les crawlers peuvent avoir du mal à l'exécuter correctement.

**Solutions :**
- Server-Side Rendering (SSR) avec Next.js
- Static Site Generation (SSG)
- Pre-rendering

### ❌ Complexité accrue

Les SPA nécessitent de gérer :
- Routing côté client (React Router)
- Gestion d'état complexe (Redux, Zustand)
- Cache des données
- Gestion d'erreurs
- Loading states partout

C'est plus complexe qu'une MPA où le serveur gère tout ça.

### ❌ JavaScript obligatoire

Si JavaScript est désactivé (ou échoue à charger), **l'application ne fonctionne pas du tout**.

Les MPA peuvent fonctionner sans JS (même si moins interactives).

## Quand utiliser une SPA ?

### ✅ Utilisez une SPA pour :

**Applications web complexes :**
- Dashboards d'administration
- Outils de productivité (type Google Docs)
- Applications de gestion (CRM, ERP)
- Réseaux sociaux
- Applications de messagerie

**Caractéristiques :**
- Beaucoup d'interactions
- Utilisateurs connectés (pas besoin de SEO)
- Expérience fluide importante
- Navigation fréquente entre les pages

**Exemples :**
- Gmail
- Figma
- Notion
- Trello
- Spotify Web

### ❌ N'utilisez PAS une SPA pour :

**Sites vitrines / blogs / e-commerce :**
- Site vitrine d'entreprise
- Blog
- Documentation
- Site e-commerce (sauf si hybride)
- Landing pages

**Pourquoi ?**
- SEO crucial (Google doit voir le contenu)
- Peu d'interactions
- Performance initiale importante
- Contenu essentiellement statique

**Meilleure option :** MPA ou framework hybride (Next.js, Remix)

## Les frameworks hybrides : le meilleur des deux mondes

### Next.js, Remix, SvelteKit, etc.

Ces frameworks offrent **SPA + MPA** :

```
┌─────────────────────────────────────────┐
│  Première visite (MPA-like)             │
│  ───────────────────────                │
│  → Serveur génère le HTML complet      │
│  → SEO parfait                          │
│  → Contenu visible immédiatement        │
└─────────────────────────────────────────┘

┌─────────────────────────────────────────┐
│  Navigation suivante (SPA-like)         │
│  ───────────────────────                │
│  → JavaScript prend le relais           │
│  → Navigation instantanée               │
│  → Pas de rechargement                  │
└─────────────────────────────────────────┘
```

<Callout type="info" title="Next.js = React avec superpowers">
**Next.js** est le framework React le plus populaire. Il ajoute :

- **SSR** (Server-Side Rendering) : Le serveur génère le HTML
- **SSG** (Static Site Generation) : Pages pré-générées
- **Routing** automatique (basé sur les fichiers)
- **API routes** (backend intégré)
- **Optimisations** automatiques

**Résultat :** SEO parfait + Expérience SPA fluide

Vous apprendrez Next.js après avoir maîtrisé React !
</Callout>

### Approches de rendu

| Approche | Description | Cas d'usage |
|----------|-------------|-------------|
| **CSR** (Client-Side Rendering) | Tout rendu dans le navigateur (SPA classique) | Dashboards, apps privées |
| **SSR** (Server-Side Rendering) | HTML généré à chaque requête | Pages dynamiques avec SEO |
| **SSG** (Static Site Generation) | HTML pré-généré au build | Blogs, docs, sites statiques |
| **ISR** (Incremental Static Regeneration) | SSG avec mise à jour périodique | E-commerce, actualités |

**React seul = CSR uniquement**
**Next.js = CSR + SSR + SSG + ISR**

## Architecture d'une SPA React

### Structure classique

```
┌──────────────────────────────────────────┐
│          Navigateur (Client)             │
│  ┌────────────────────────────────────┐  │
│  │       Application React            │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │   Composants React           │  │  │
│  │  │   (UI, logique)              │  │  │
│  │  └──────────────────────────────┘  │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │   React Router               │  │  │
│  │  │   (navigation)               │  │  │
│  │  └──────────────────────────────┘  │  │
│  │  ┌──────────────────────────────┐  │  │
│  │  │   State Management           │  │  │
│  │  │   (useState, Context, etc.)  │  │  │
│  │  └──────────────────────────────┘  │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
                    ↕ HTTP (JSON)
┌──────────────────────────────────────────┐
│             Serveur (Backend)            │
│  ┌────────────────────────────────────┐  │
│  │        API REST / GraphQL          │  │
│  │   (Node.js, Python, Java, etc.)    │  │
│  └────────────────────────────────────┘  │
│  ┌────────────────────────────────────┐  │
│  │          Base de données           │  │
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

### Communication Frontend ↔ Backend

```tsx
// Frontend React (SPA)
function UserList() {
  const [users, setUsers] = useState([]);

  useEffect(() => {
    // Appel API au backend
    fetch('https://api.monapp.com/users')
      .then(res => res.json())
      .then(data => setUsers(data));
  }, []);

  return (
    <ul>
      {users.map(user => (
        <li key={user.id}>{user.name}</li>
      ))}
    </ul>
  );
}
```

Le frontend **ne parle qu'avec l'API** (JSON uniquement).

## Exemples pratiques

### SPA : Application de gestion de tâches

```tsx
// Tout se passe côté client
function TodoApp() {
  const [todos, setTodos] = useState([]);

  // Ajouter une tâche (pas de rechargement)
  const addTodo = (text) => {
    setTodos([...todos, { id: Date.now(), text }]);
  };

  // Supprimer une tâche (pas de rechargement)
  const deleteTodo = (id) => {
    setTodos(todos.filter(t => t.id !== id));
  };

  return (
    <div>
      <TodoForm onAdd={addTodo} />
      <TodoList todos={todos} onDelete={deleteTodo} />
    </div>
  );
}

// Navigation sans rechargement
<Link to="/todos">Mes tâches</Link>
<Link to="/profile">Profil</Link>
```

### MPA : Site vitrine traditionnel

```php
<!-- page-accueil.php -->
<?php include 'header.php'; ?>
<h1>Accueil</h1>
<p>Bienvenue sur notre site</p>
<a href="contact.php">Contactez-nous</a> <!-- Rechargement complet -->
<?php include 'footer.php'; ?>

<!-- contact.php -->
<?php include 'header.php'; ?>
<h1>Contact</h1>
<form method="POST">...</form> <!-- Rechargement au submit -->
<?php include 'footer.php'; ?>
```

Chaque page = fichier séparé, rechargement complet.

## Résumé

<Callout type="success" title="Ce qu'il faut retenir">
**SPA (Single Page Application) :**
- Une seule page HTML, tout le reste en JavaScript
- Navigation fluide sans rechargement
- React crée des SPA par défaut
- ✅ Parfait pour : apps complexes, dashboards, outils
- ❌ Problèmes : SEO, chargement initial

**MPA (Multi-Page Application) :**
- Chaque page = requête serveur + rechargement
- Architecture traditionnelle du web
- ✅ Parfait pour : sites vitrines, blogs, SEO
- ❌ Problème : navigation moins fluide

**Frameworks hybrides (Next.js) :**
- Combinent SPA + MPA
- SEO parfait + Navigation fluide
- Le meilleur des deux mondes

**Pour ce cours :**
- Vous apprendrez d'abord React pur (SPA)
- Vous découvrirez Next.js plus tard (hybride)
</Callout>
