## Pratiques React

<QuickCheck
  question="4. Qu'est-ce que le Single Responsibility Principle pour les composants ?"
  options={[
    "Un composant doit avoir une seule responsabilité, une raison de changer",
    "Un composant ne doit avoir qu'une seule fonction",
    "Un composant doit être utilisé une seule fois",
    "Un composant ne peut avoir qu'un seul état"
  ]}
  correctAnswer={0}
  explanation="✅ Single Responsibility = un composant fait UNE chose et la fait bien. Si un composant gère users + products + orders + stats, il fait trop et doit être divisé. ❌ Ce n'est pas limité au nombre de fonctions dans le code. ❌ Un composant peut être réutilisé plusieurs fois. ❌ Un composant peut avoir plusieurs états si nécessaire. Le principe : diviser pour conquérir, faciliter la maintenance."
/>

<QuickCheck
  question="5. Quelle convention de nommage pour les event handlers dans un composant ?"
  options={[
    "handle* (ex: handleClick, handleSubmit)",
    "on* (ex: onClick, onSubmit)",
    "do* (ex: doClick, doSubmit)",
    "action* (ex: actionClick, actionSubmit)"
  ]}
  correctAnswer={0}
  explanation="✅ Convention : handle* pour les fonctions définies dans le composant (handleClick, handleSubmit, handleChange). ❌ on* est réservé pour les props passées aux composants enfants. ❌ do* et action* ne sont pas des conventions React standard. Exemple : const handleClick = () => {} dans le composant, puis <button onClick={handleClick}>. Cohérence = lisibilité."
/>

<QuickCheck
  question="6. Pourquoi ne faut-il JAMAIS muter l'état directement ?"
  options={[
    "React ne détecte pas les changements, pas de re-render",
    "Ça ralentit l'application",
    "C'est interdit en TypeScript",
    "Ça supprime toutes les données"
  ]}
  correctAnswer={0}
  explanation="✅ React compare les références d'objets/tableaux. Si vous mutez directement (users.push()), la référence reste la même, React ne détecte PAS le changement et ne re-render pas. ❌ Ce n'est pas une question de performance. ❌ TypeScript ne l'empêche pas automatiquement. ❌ Ça ne supprime rien mais casse la réactivité. Toujours créer de nouveaux objets/tableaux : setUsers([...users, newUser])."
/>

<QuickCheck
  question="7. Quand faut-il diviser un composant en plusieurs ?"
  options={[
    "Quand il dépasse 150 lignes, ou a une logique réutilisable",
    "Toujours diviser au maximum, 1 ligne par composant",
    "Jamais, garder tout dans un seul fichier",
    "Seulement quand l'IA le suggère"
  ]}
  correctAnswer={0}
  explanation="✅ Divisez quand : > 150 lignes, logique réutilisable ailleurs, séparation claire des responsabilités, ou amélioration de la lisibilité. ❌ Sur-diviser rend le code aussi difficile à maintenir que sous-diviser. ❌ Un composant géant (300+ lignes) est impossible à maintenir. ❌ Ne vous fiez pas uniquement aux suggestions de l'IA. Règle d'or : une responsabilité = un composant."
/>

Structure = scalabilité et maintenabilité."
/>

Organisation claire = code maintenable et facile à trouver."
/>

## Custom Hooks

<QuickCheck
  question="10. Qu'est-ce qu'un custom hook ?"
  options={[
    "Une fonction JavaScript qui utilise des hooks React",
    "Un composant React spécial",
    "Une méthode de classe",
    "Une librairie externe"
  ]}
  correctAnswer={0}
  explanation="✅ Un custom hook est une fonction JavaScript (use*) qui utilise des hooks React (useState, useEffect, etc.) pour extraire et réutiliser de la logique stateful. ❌ Ce n'est pas un composant (pas de JSX retourné). ❌ Les hooks n'existent pas dans les class components. ❌ Ce n'est pas une librairie, c'est du code que vous écrivez. Exemple : useFetch pour réutiliser la logique de fetch."
/>

<QuickCheck
  question="11. Quelle convention de nommage pour les custom hooks ?"
  options={[
    "Toujours commencer par 'use' (ex: useFetch)",
    "Commencer par 'custom' (ex: customFetch)",
    "Pas de convention spécifique",
    "Commencer par 'hook' (ex: hookFetch)"
  ]}
  correctAnswer={0}
  explanation="✅ Convention obligatoire : les hooks commencent TOUJOURS par 'use' (useFetch, useLocalStorage, useForm). ❌ 'custom' n'est pas la convention React. ❌ La convention existe et est importante pour que React reconnaisse les hooks. ❌ 'hook' n'est pas la convention. Le préfixe 'use' permet à React d'appliquer les règles des hooks automatiquement. C'est une règle, pas une suggestion."
/>

<QuickCheck
  question="12. Que retourne généralement un custom hook ?"
  options={[
    "Un objet ou tableau avec état et fonctions",
    "Toujours du JSX",
    "Uniquement des strings",
    "Rien (void)"
  ]}
  correctAnswer={0}
  explanation="✅ Custom hooks retournent généralement : un objet { data, loading, error } ou un tableau [value, setValue] comme useState. ❌ Les hooks ne retournent PAS de JSX - ça c'est pour les composants. ❌ Ils peuvent retourner n'importe quel type de données. ❌ Ils retournent presque toujours quelque chose d'utile. Exemple : useFetch retourne { data, loading, error }, useLocalStorage retourne [value, setValue]."
/>

## Autres Hooks

<QuickCheck
  question="13. À quoi sert useRef ?"
  options={[
    "Créer une référence qui persiste sans déclencher de re-render",
    "Créer un état comme useState",
    "Faire des appels API",
    "Gérer les routes"
  ]}
  correctAnswer={0}
  explanation="✅ useRef crée une référence mutable qui persiste entre les rendus SANS déclencher de re-render. Utilisé pour : accéder aux éléments DOM (inputRef.current.focus()), stocker des valeurs techniques (timers, previous values). ❌ Pour l'état qui affiche dans l'UI, utilisez useState. ❌ Pour les API, utilisez useEffect + fetch ou un custom hook. ❌ Pour les routes, utilisez React Router. useRef = valeurs techniques sans re-render."
/>

<QuickCheck
  question="14. Quelle est la différence entre useRef et useState ?"
  options={[
    "useRef ne déclenche pas de re-render, useState oui",
    "Aucune différence",
    "useRef est plus rapide",
    "useState est obsolète"
  ]}
  correctAnswer={0}
  explanation="✅ La différence clé : useState déclenche un re-render quand la valeur change, useRef ne déclenche JAMAIS de re-render. ❌ Ce sont des hooks différents avec des usages différents. ❌ Ce n'est pas une question de vitesse mais de comportement. ❌ useState est fondamental en React, pas obsolète. Utilisez useState pour les données affichées, useRef pour les valeurs techniques (timers, références DOM)."
/>

<QuickCheck
  question="15. Quand utiliser useMemo ?"
  options={[
    "Pour mémoriser le résultat d'un calcul coûteux",
    "Pour tous les calculs, toujours",
    "Pour créer des états",
    "Pour faire des appels API"
  ]}
  correctAnswer={0}
  explanation="✅ useMemo mémorise le résultat d'un calcul coûteux pour éviter de le recalculer à chaque render. Utilisez-le seulement si le calcul est vraiment lourd. ❌ Ne l'utilisez pas partout - ça ajoute de la complexité et peut ralentir. ❌ Pour l'état, utilisez useState. ❌ Pour les API, utilisez useEffect. Règle : optimisez seulement quand nécessaire, pas prématurément."
/>

<QuickCheck
  question="16. À quoi sert useCallback ?"
  options={[
    "Mémoriser une fonction pour éviter de la recréer",
    "Créer des fonctions asynchrones",
    "Remplacer useState",
    "Faire des appels API"
  ]}
  correctAnswer={0}
  explanation="✅ useCallback mémorise une fonction pour qu'elle garde la même référence entre les renders. Utile pour : passer des callbacks à des composants enfants mémorisés, éviter des re-renders inutiles. ❌ Ce n'est pas pour créer des async/await. ❌ Il ne remplace pas useState. ❌ Pour les API, utilisez useEffect. Comme useMemo : optimisez seulement si nécessaire."
/>
