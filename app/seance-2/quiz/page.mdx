## JSX Syntax

<QuickCheck

  options={[

    "Pour différencier les classes CSS des classes JavaScript",
    "Il n'y a aucune raison particulière"
  ]}
  correctAnswer={0}
  explanation="✅ En JavaScript, class est un mot réservé pour les classes ES6 (class MyClass {}). React utilise donc className pour éviter les conflits. ❌ Ce n'est pas juste une convention, c'est une nécessité technique. ❌ La différenciation n'est pas la raison principale. Même logique pour htmlFor au lieu de for (boucles for)."
/>

<QuickCheck
  question="7. Que fait ce code JSX : <>{content}</> ?"
  options={[

    "Crée un span invisible"
  ]}
  correctAnswer={0}
  explanation="✅ <></> est un raccourci pour <React.Fragment></React.Fragment>. Les fragments permettent de grouper plusieurs éléments sans ajouter de div ou autre balise dans le DOM. ❌ Contrairement à une div, le fragment n'ajoute AUCUN nœud. ❌ C'est une syntaxe valide et courante. ❌ Ce n'est pas un span. Utilisez les fragments pour éviter les div inutiles !"
/>

<QuickCheck
  question="8. Comment insérer une expression JavaScript dans du JSX ?"
  options={[

    "Avec des crochets : [expression]",
    "Directement sans délimiteurs"
  ]}
  correctAnswer={0}
  explanation="✅ Les accolades {} permettent d'insérer des expressions JavaScript : {name}, {2 + 2}, {user.age}. ❌ Les parenthèses () sont pour grouper du JSX multi-lignes. ❌ Les crochets [] sont pour les tableaux. ❌ Sans délimiteurs, c'est du texte littéral. Attention : {if(x){}} ne fonctionne pas (pas une expression), utilisez le ternaire {x ? 'oui' : 'non'}."
/>

Parfait pour les layouts et wrappers !"

## Listes et Keys

<QuickCheck
  question="13. Pourquoi la prop key est-elle obligatoire dans les listes ?"
  options={[
    "Pour que React identifie quels éléments ont changé et optimise le rendu",
    "Pour éviter les erreurs de compilation",
    "C'est une exigence TypeScript",
    "Pour trier automatiquement la liste"
  ]}
  correctAnswer={0}
  explanation="✅ Les keys permettent à React d'identifier les éléments par identité (key='user-1') au lieu de position (élément 0, 1, 2). React sait ainsi quels éléments ont changé, été ajoutés ou supprimés → meilleures performances et moins de bugs. ❌ Ça compile sans key, mais génère un warning. ❌ Rien à voir avec TypeScript. ❌ Les keys n'affectent pas le tri. Toujours utiliser un ID unique !"
/>

<QuickCheck
  question="14. Quelle est la MAUVAISE pratique pour les keys ?"
  options={[
    "Utiliser l'index du tableau comme key si la liste peut changer",
    "Utiliser un ID unique de la base de données",
    "Utiliser une propriété unique et stable (email, slug)",
    "Générer un UUID pour chaque élément"
  ]}
  correctAnswer={0}
  explanation="✅ NE JAMAIS utiliser l'index comme key si la liste peut changer (ajout, suppression, tri) ! L'index change → React perd la trace des éléments. ✅ ID de BDD = excellent (toujours unique et stable). ✅ Propriété unique = bon si vraiment unique. ✅ UUID = acceptable mais overkill. Exemple problème : supprimer 'Bob' (index 1) fait que Charlie prend l'index 1 → confusion pour React."
/>

## Rendu Conditionnel

<QuickCheck
  question="15. Quelle syntaxe utiliser pour un rendu conditionnel simple dans le JSX ?"
  options={[
    "L'opérateur ternaire : {condition ? <A /> : <B />}",
    "if/else directement dans le JSX : {if (x) <A />}",
    "switch/case : {switch(x) { case 1: <A /> }}",
    "while : {while(x) <A />}"
  ]}
  correctAnswer={0}
  explanation="✅ Le ternaire est parfait pour choisir entre deux options dans le JSX : {isLoggedIn ? <Dashboard /> : <Login />}. ❌ if/else sont des DÉCLARATIONS, pas des EXPRESSIONS → impossible dans {}. ❌ switch/case pareil, pas une expression. ❌ while est une boucle, pas pour le rendu conditionnel. Alternative : early return avec if/else AVANT le return du composant."
/>

<QuickCheck
  question="16. Que fait l'opérateur && dans ce code : {isLoggedIn && <Dashboard />} ?"
  options={[
    "Affiche <Dashboard /> si isLoggedIn est true, sinon n'affiche rien",
    "Affiche <Dashboard /> si isLoggedIn est false",
    "C'est une erreur de syntaxe",
    "Affiche toujours <Dashboard />"
  ]}
  correctAnswer={0}
  explanation="✅ L'opérateur && (ET logique) affiche le deuxième élément si le premier est truthy. Si isLoggedIn = true, affiche <Dashboard />. Si false, n'affiche rien (null). ❌ Ce n'est pas une négation. ❌ C'est une syntaxe valide et très courante. ❌ Il faut que la condition soit vraie. Attention au piège : {count && <Text />} affiche '0' si count = 0 (0 est falsy mais affiché) !"
/>

<QuickCheck

    "TypeScript détecte automatiquement les types",
    "Ce n'est pas possible de typer les props"
  ]}
  correctAnswer={0}
  explanation="✅ Créez une interface pour les props : interface UserCardProps { name: string; age: number; }, puis function UserCard({ name, age }: UserCardProps). ❌ JSDoc fonctionne mais TypeScript c'est mieux. ❌ TypeScript n'infère PAS automatiquement les props (contrairement aux variables). ❌ C'est tout l'intérêt de TypeScript avec React ! Alternative : type Props = { name: string }."
/>

  options={[
    "interface peut être étendue et fusionnée, type est plus flexible pour les unions",
    "type est obsolète, utilisez toujours interface",
    "interface est plus rapide à l'exécution",
    "Il n'y a aucune différence"
  ]}
  correctAnswer={0}
  explanation="✅ interface peut être étendue (extends) et déclarée plusieurs fois (fusion). type peut créer des unions (type Status = 'loading' | 'success') et des alias complexes. ❌ type n'est PAS obsolète, chacun a son usage. ❌ TypeScript est supprimé à la compilation, pas de différence d'exécution. ❌ Différences subtiles mais importantes. Pour les props React : les deux fonctionnent, interface est conventionnel."
/>
