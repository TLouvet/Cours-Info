## Custom Hooks

<QuickCheck
  question="5. Qu'est-ce qu'un custom hook ?"
  options={[
    "Une fonction JavaScript qui utilise des hooks React",
    "Un composant React spécial",
    "Une méthode de classe",
    "Une librairie externe"
  ]}
  correctAnswer={0}
  explanation="✅ Un custom hook est une fonction JavaScript (préfixée use*) qui utilise des hooks React (useState, useEffect, etc.) pour extraire et réutiliser de la logique stateful. ❌ Ce n'est pas un composant — il ne retourne pas de JSX. ❌ Les hooks n'existent pas dans les class components. ❌ Ce n'est pas une librairie, c'est du code que vous écrivez vous-même."
/>

<QuickCheck
  question="6. Quelle convention de nommage pour les custom hooks ?"
  options={[
    "Toujours commencer par 'use' (ex: useFetch, useQuiz)",
    "Commencer par 'custom' (ex: customFetch)",
    "Pas de convention spécifique",
    "Commencer par 'hook' (ex: hookFetch)"
  ]}
  correctAnswer={0}
  explanation="✅ Convention obligatoire : les hooks commencent TOUJOURS par 'use'. Ce préfixe permet à React (et aux linters) d'appliquer les règles des hooks automatiquement. ❌ 'custom', 'hook' ou aucune convention ne sont pas reconnus par React. C'est une règle, pas une suggestion."
/>

<QuickCheck
  question="7. Quel est le principal avantage d'extraire la logique dans un custom hook ?"
  options={[
    "Réutiliser la logique stateful dans plusieurs composants",
    "Rendre le composant plus lent",
    "Éviter d'utiliser useState",
    "Supprimer les props"
  ]}
  correctAnswer={0}
  explanation="✅ Les custom hooks permettent d'extraire et réutiliser de la logique stateful (état + effets) sans dupliquer le code. Le composant devient plus lisible car il ne contient plus que du JSX. ❌ Les hooks n'ont pas d'impact négatif sur les performances. ❌ Les hooks utilisent useState en interne. ❌ Les props restent le mécanisme de passage de données entre composants."
/>

<QuickCheck
  question="8. Que retourne généralement un custom hook ?"
  options={[
    "Un objet ou tableau avec état et fonctions",
    "Toujours du JSX",
    "Uniquement des strings",
    "Rien (void)"
  ]}
  correctAnswer={0}
  explanation="✅ Custom hooks retournent généralement : un objet { data, loading, error } ou un tableau [value, setValue] comme useState. ❌ Les hooks ne retournent PAS de JSX — c'est réservé aux composants. ❌ Ils peuvent retourner n'importe quel type. ❌ Ils retournent presque toujours quelque chose d'utile. Exemple : useLocalStorage retourne [value, setValue]."
/>

## Autres Hooks

<QuickCheck
  question="9. À quoi sert useRef ?"
  options={[
    "Créer une référence qui persiste sans déclencher de re-render",
    "Créer un état comme useState",
    "Faire des appels API",
    "Gérer les routes"
  ]}
  correctAnswer={0}
  explanation="✅ useRef crée une référence mutable qui persiste entre les rendus SANS déclencher de re-render. Utilisé pour : accéder aux éléments DOM (inputRef.current.focus()), stocker des valeurs techniques (timers, previous values). ❌ Pour l'état affiché dans l'UI, utilisez useState. ❌ Pour les API, utilisez useEffect + fetch. ❌ Pour les routes, utilisez React Router."
/>

<QuickCheck
  question="10. Quelle est la différence entre useRef et useState ?"
  options={[
    "useRef ne déclenche pas de re-render, useState oui",
    "Aucune différence",
    "useRef est plus rapide que useState",
    "useState est obsolète"
  ]}
  correctAnswer={0}
  explanation="✅ La différence clé : useState déclenche un re-render quand la valeur change, useRef ne déclenche JAMAIS de re-render. Utilisez useState pour les données affichées, useRef pour les valeurs techniques (timers, références DOM). ❌ Ce sont des hooks différents avec des usages différents. ❌ Ce n'est pas une question de vitesse mais de comportement."
/>

<QuickCheck
  question="11. Quand utiliser useMemo ?"
  options={[
    "Pour mémoriser le résultat d'un calcul coûteux qui ne doit pas se recalculer à chaque render",
    "Pour tous les calculs, toujours",
    "Pour créer des états",
    "Pour faire des appels API"
  ]}
  correctAnswer={0}
  explanation="✅ useMemo mémorise le résultat d'un calcul coûteux pour éviter de le recalculer à chaque render. Utilisez-le seulement si le calcul est vraiment lourd — et seulement une fois que l'app fonctionne. ❌ L'utiliser partout ajoute de la complexité inutile. ❌ Pour l'état, utilisez useState. ❌ Pour les API, utilisez useEffect."
/>

<QuickCheck
  question="12. À quoi sert useCallback ?"
  options={[
    "Mémoriser une fonction pour stabiliser sa référence entre les renders",
    "Créer des fonctions asynchrones",
    "Remplacer useState",
    "Faire des appels API"
  ]}
  correctAnswer={0}
  explanation="✅ useCallback mémorise une fonction pour qu'elle garde la même référence entre les renders. Utile quand on passe un callback à un composant enfant mémorisé avec React.memo. Vous verrez souvent ce hook dans des warnings ESLint. ❌ Ce n'est pas pour créer des async/await. ❌ Il ne remplace pas useState. Comme useMemo : n'optimisez que si nécessaire."
/>

Installez React DevTools — c'est indispensable !"

  ]}
  correctAnswer={0}

Très commune quand les données d'API ne sont pas encore chargées. ❌ React fonctionne bien, c'est votre code. ❌ Ce n'est pas un virus. ❌ Node.js n'a rien à voir."
/>

<QuickCheck
  question="15. Quelle est la cause la plus fréquente de 'Too many re-renders' ?"
  options={[
    "Un setState appelé directement dans le corps du composant (pas dans un handler ou useEffect)",
    "Trop de composants dans l'application",
    "Une connexion internet lente",
    "Un fichier CSS trop grand"
  ]}
  correctAnswer={0}
  explanation="✅ React déclenche cette erreur quand un composant se re-rend en boucle infinie. Cause fréquente : setState() appelé directement dans le rendu au lieu d'un event handler. ❌ Le nombre de composants n'a pas d'impact. ❌ C'est une erreur JavaScript, pas réseau. ❌ Le CSS n'affecte pas les re-renders."
/>
